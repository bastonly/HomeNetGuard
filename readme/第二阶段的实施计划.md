# 系统自动升级与安全逻辑优化方案

本项目包含系统自动升级流程的设计，以及针对近期发现的“因系统资源分配失败导致误报篡改”问题的安全逻辑优化。

## 调查报告：误报篡改导致授权冻结

### 问题描述
用户反馈在 18:03:40 系统检测到“本地数据篡改”，导致授权自动冻结。

### 调查结果
1. **根本原因**：在 18:03:39 附近，系统日志显示 `popen() failed!`。这通常发生在系统资源（进程数或文件描述符）达到上限时。
2. **逻辑连锁反应**：
   - 随后的 `LicenseManager::is_license_valid()` 检查调用了 `get_device_fingerprint()`。
   - `get_device_fingerprint()` 内部依赖 `popen()` 获取 UUID、MAC 和 Serial。
   - 由于 `popen()` 连续失败，获取到的硬件标识为空，函数回退并返回了默认值 `"000000000000"`。
   - 授权检查逻辑对比了基于全零标识计算的 HMAC 输出，与本地保存的（基于真实硬件 ID）HMAC，发现不符。
   - 系统误判为用户手动修改了配置文件，触发了 `suspend_tampered_license` 惩罚逻辑，强行将状态设为 `revoked`。

- **审慎惩罚**：在授权有效性检查时，若因系统环境异常（如无法获取硬件 ID）导致校验中断，应记录错误并报警，但**绝对禁止**执行惩罚性的状态吊销操作操作。只有在“成功获取到有效但不匹配的硬件 ID”时才判定为篡改。
- **业务规则对齐**：明确“吊销 (revoked)”状态不适用宽限期。若云端返回 `revoked`，系统必须立即停止一切保护服务，且不为其开启任何 30 天缓冲。只有 `expired`（过期）或 `suspended`（挂起/断网）状态才保留宽限期。
- **全状态哈希绑定 (State-Bound HMAC)**：
    - 将 `LICENSE_STATUS` 和 `DEVICE_STATUS` 字符串加入 HMAC 计算载荷。
    - **全状态重算**：无论云端返回何种状态（active, suspended, revoked, expired 等），每次成功 `checkin` 并更新本地状态后，必须立即重新计算并保存对应的 HMAC。
    - 使签名不仅绑定“时间”，更绑定“状态”。手动修改状态而不修改签名将导致校验失败。
- **强制校验逻辑**：
    - `is_license_valid()` 将不再盲目信任任何本地状态字段，而是首先校验 `OFFLINE_MAC` 与当前文件内容是否匹配。
    - 移除 `status == "active"` 的早期放行逻辑，确保所有状态变更必须经过合法的 `checkin` 或 `activate` 流程。
- **服务器响应身份验签 (Server Response Authentication)**：
    - **挑战回避**：为了防止伪造服务器攻击，服务器下发的 JSON 报文应包含 `signature` 字段。
    - **双向校验**：客户端不仅通过 HMAC 保护本地文件，还必须通过内置的 **RSA 公钥** 验证服务器返回数据的真实性。
    - **原理**：即使 DNS 被劫持，伪造服务器由于没有服务端的私钥，无法产生合法的回应签名，客户端将拒绝更新本地状态。
