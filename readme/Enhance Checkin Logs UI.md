离线宽限期功能实现计划
我们需要实现一个安全且防篡改的 30 天离线宽限期。该逻辑必须能够抵御用户的恶意操作，例如修改系统时钟或直接编辑离线状态 JSON 文件。

机制设计
触发条件：当 checkin() 签到失败（网络错误或服务器返回 500 等）并在之前并未开始倒计时时，系统开始计算宽限期。
安全状态存储：
将 GRACE_START_TIME（首次失败发生时的系统时间）和 LAST_CHECKIN_TIME（最后成功签到时间）保存为一个离线的 JSON 文件。
使用 HMAC-SHA256 对该 JSON 文件进行签名。HMAC 的密钥将根据硬件的 device_fingerprint() 动态生成，以防止将状态文件复制到其他设备或被手动篡改。
验证逻辑：
在允许离线运行服务之前，is_license_valid() 必须重新计算并验证 HMAC 签名。
如果签名匹配且 (当前时间 - GRACE_START_TIME) <= 30 天，则允许运行。
如果签名不匹配（表示发生篡改），则拒绝运行。
如果时间出现倒流（即当前时间 < GRACE_START_TIME - 允许的误差范围），则怀疑用户篡改了时钟，同样拒绝运行。

### 为什么会显示 127.0.0.1？
1. **内部转发**：您的浏览器访问的是路由器的 80 或 443 端口，而 Python 后端 API 运行在本地的 `5000` 端口。
2. **连接来源**：当请求从外部到达路由器后，前面的代理服务（如 Nginx）会接收它，然后再在路由器本地“内部发起”一个新的请求提供给 Python。
3. **识别结果**：对于 Python 后端来说，它感知到的连接确实是来自本地代理的 `127.0.0.1`，而不是您的真实内网 IP `192.168.0.152`。
